# データ源と根拠（タイホウ亀島店 ジャグラー/ハナハナ設定狙い）

「どこから何を取るか」「なぜそれで設定が分かると言えるのか」「何が言えて何が言えないか」のまとめ。
調査日: 2026-11-11。サイト側の仕様は変わるので、動かなくなったらここを見直す。

## 1. 何をどこから取るか

| 知りたいこと | 取り元 | 取り方 | 確かさ |
|---|---|---|---|
| 全台の日次 差枚・G数（長期の傾向、凹み、入替の検知） | みんレポ (min-repo.com) | `run.mjs` が自動取得（自宅回線） | 第三者の独自調査値（推定）。長期・全台そろうのが強み |
| ジャグラー/ハナハナの台番別 **総G・BIG・REG** | 店の公式台データ（台データオンライン系） | **自動取得しない。** 見て `data/manual/counts.csv` に写す | 店のデータ機の実数。設定推定の根拠として一番強い |
| 示唆景品・札・朝一の挙動など現地でしか分からないこと | 自分の目 | `data/manual/observations.csv` に 日付×台番×タグ で記録 | 記録の仕方しだい（下の「記録の偏り」参照） |
| 入替日・店休日 | 店の告知（公式X・P-WORLD・DMMぱちタウン） | `data/manual/calendar.csv` に手入力 + 設置構成の変化から自動検知 | 告知は確実。自動検知は 1〜2 日ずれることがある |
| 景品示唆・おすすめ週間など店側の動き | 店内（カウンター・POP）、公式X・LINE | `calendar.csv` に日付（期間）・種類・対象機種を手入力 | 自分で見たものが一番確か。先の日付も書ける |
| 年金支給日・給料日・連休 | 暦から自動計算 | 何もしなくてよい（年金は偶数月15日、土日なら直前の金曜） | 確実 |
| 設定ごとのボーナス確率・機械割 | 解析サイトの掲載値（パチ7・なな徹・DMMぱちタウン・P-WORLD・一撃） | `lib/specs.mjs` に 14 機種を収録（確認元 URL つき） | 各機種 2 サイト以上で一致を確認。新機種が入ったら追記が必要 |
| 口コミ・旧イベント日 | みんパチの店舗ページ | 読むだけ（仮説の種） | 個人の感想。そのまま信じず検証対象にする |

### みんレポ（既存の自動取得）

- 取れるもの: 日ごとの 機種別（平均差枚・平均G数・勝率・出率）、機種別詳細ページの台番別 差枚・G数、末尾別。
- 台番別ページに BB/RB 列がある場合は自動で取り込む実装になっている（`parse.mjs` の `columnMap`）。
  **この店のページに BB/RB 列があるかは未確認**（下記のとおりクラウドからは中身が見えないため）。
  初回取得後に `data/units.csv` の `bb` `rb` 列が埋まっているかを見れば分かる。
- 制約: データセンター系 IP には中身を返さない。2026-11-11 にクラウド環境から確認したところ、
  記事一覧 API・店舗タグページとも HTTP 200 で本文が空だった。ダミー値（差枚 0/±1）を返すこともある（`detectMasked` が検知して中断する）。
  これはサイト側が機械的なアクセスを歓迎していない合図でもある。自宅回線から、間隔を空けて、必要な分だけ取ること（README の注意を守る）。
  利用規約はこの環境から読めていないので、一度自分のブラウザで確認しておくこと。

### 店の公式台データ（手で写す）

- 公式サイト (taiho-group.net) の「利用規約」ページは **「台DATA ONLINEサービス利用規約」（運営: 株式会社GOLUCK）** そのもの。
  つまり公式の台データは台データオンライン系のサービスで提供されている。みんパチの店舗ページは台データのリンク先として
  `taiho-group.net/kamejima/daidata` を挙げている（PC からのアクセスでは 404 だった。スマホ向けページかアプリ内の可能性。要確認）。
  P-WORLD / DMMぱちタウンの店舗ページには「台データはアプリでご覧いただけます」とある。
- 規約に「データベース等を複製…する行為」の禁止（第4条10）と「掲載情報を第三者に提供してはならない」（第13条2）がある。
  → **プログラムでの一括取得は作らない。** 画面を見て、ジャグラー/ハナハナの台だけを自分用に書き写す（`counts.csv` は gitignore 済みで公開されない）。
- 写す項目: 総ゲーム数・BIG 回数・REG 回数（差枚が出ていればそれも）。台データオンライン系は通常、直近 1 週間ぶんほど遡れるので、
  毎日でなくても週 1〜2 回まとめて写せば穴は空かない（遡れる日数は実際の画面で確認すること）。
- `node tools/minrepo/run.mjs sheet --date 2026-11-10` で、その日のジャグラー/ハナハナ全台ぶんの記入行が `counts.csv` に足される。

### 入替日

- 公式サイトの「最新情報」は告知が画像だけで、日付・機種名をテキストで取れない（2026-11-11 確認）。
- 告知を見る場所: 公式 X `@TAIHO_kamejima`、[P-WORLD の店舗ページ](https://www.p-world.co.jp/aichi/taihou-kamejima.htm)、
  [DMMぱちタウン](https://p-town.dmm.com/shops/aichi/5713)。見たら `calendar.csv` に `2026-11-17,入替,` のように 1 行足す。
- 過去ぶんは、みんレポの機種一覧に「新しい機種が現れた / 台数が増えた」日から自動検知する（既定: 3 台以上増えた日）。

### 口コミから拾った仮説（みんパチ。検証前の「種」）

- 旧イベント日は「3のつく日」「第1土曜日」。
- 「3の日はハナハナに 5・6 が 5 台に 1 台くらい入る。平日も 40 台中 3〜4 台に強めの中間」（2021-02）
- 「ハナは頑張っているが、ジャグラーやボーナスタイプは厳しい」（2021-08）、「3の日にジャグラーはあんまりだがハナはそこそこ」（2024-02）
- 「新台入替の初日に回収」（2022-10）、「土日は回収日」（2025-02）
- どれも個人の感想で時期も古い。このツールの「機種別」「イベント日」「入替日」の表が、今のデータで同じことを言っているかを見る。

### 収支に効く店の条件（みんパチ掲載値。要確認）

- 20円スロットは **7.0枚交換**（非等価）。現金で借りたメダルは 1 枚あたり約 5.7 円の換金ギャップが出る
  （1,000円=50枚で借りて、50枚を換金すると約714円）。現金投資 500 枚なら約 2,860 円 ≒ 200 枚ぶん。
- 貯メダルの再プレイは 1 日 500 枚まで手数料なし。**再プレイで打てる範囲に収めるほど、同じ設定でも期待収支が良くなる。**
- つまり「機械割 100% 超」でも、現金投資がかさむとマイナスになり得る。狙う基準は等価の店より高めに置く。

## 2. なぜそれで設定が分かると言えるのか

- ジャグラー/ハナハナは設定によって BIG・REG の当選確率が違い、その値は解析サイトに掲載されている
  （メーカー公表値、または各サイトの独自調査値。`lib/specs.mjs` に確認元を書いてある）。
  たとえばマイジャグラーV の REG は設定1 で 1/409.6、設定6 で 1/229.1。8,000G 回すと REG は平均 19.5 回 vs 34.9 回になる。
- 収録機種: ネオアイムジャグラーEX / アイムジャグラーEX / マイジャグラーVI / マイジャグラーV / ファンキージャグラー2 /
  ハッピージャグラーVⅢ / ゴーゴージャグラー3 / ジャグラーガールズSS / ミスタージャグラー / ウルトラミラクルジャグラー /
  キングハナハナ-30 / ドラゴンハナハナ〜閃光〜-30 / スターハナハナ-30 / ハナハナホウオウ〜天翔〜-30。
  P-WORLD の店舗ページで設置が確認できたのは マイジャグラーVI・ネオアイムジャグラーEX・ゴーゴージャグラー3（ハナハナ系は機種名を読み取れず未確認）。
  ニューキングハナハナV-30 は BT 搭載の別タイプなので対象外（設置されていればレポートに「スペック未登録」と出る）。
- ぶどう/ベル確率は設定差が小さく、掲載値もサイトによって違うため未収録。まずは BIG・REG 回数だけで判別する。
- 「総G・BIG・REG」が分かれば、「設定 s だったらこの結果が出る確率」を設定 1〜6 それぞれ厳密に計算できる（`lib/settei.mjs` の `logLikCounts`）。
  それに「この店の設定配分」を掛けて正規化したものが、その台×日の設定の確率（ベイズ推定）。
- 店の設定配分そのものは、全台×日の結果をいちばんうまく説明する配分として推定する（EM 法。`emMix`）。
  「低設定が大半の店で少し良い数字が出ても、低設定の上振れである可能性が高い」という事情を自動で織り込むための前提になる。
- BIG/REG が無く差枚と G数だけのときは、設定ごとの差枚の期待値（IN × (機械割−1)）とばらつきから同じ計算をする（`logLikDiff`）。
  ただしマイジャグラーV 8,000G で、差枚のばらつき（標準偏差）は約 1,400〜1,550 枚、設定1 と 6 の期待差枚の差は約 3,000 枚。
  1 台 1 日ではかなりぼやける。**差枚だけのデータは「束ねて傾向を見る」用**と割り切る。

### 1 台 1 日で断定できない、という前提

設定 1 でも 1 日だけなら設定 6 のような数字は普通に出る。なのでこのツールは「この台は設定 6 だ」とは言わず、

- 条件（凹み台・入替日・示唆景品つき…）ごとに台×日を束ねて、高設定の割合が他より高いかを見る
- その差が偶然で出る確率（p 値）を並べ替え検定で出す
- 見つけた法則で台を選んでいたら過去に勝てていたかを、**その日より前のデータだけ**で選び直して確かめる（ウォークフォワード検証）

の 3 段で判断する。

## 3. 検証している仮説と見方

| 仮説 | 条件の作り方 | 見る場所（レポート） |
|---|---|---|
| 凹み台に設定を入れる | 前日の差枚 / 直近 7 日の合計 / 連続マイナス日数（すべて当日より前） | 「A凹み」 |
| 良い台を据え置く | 前日の推定設定（低そう/中間/高そう）→ 当日 | 「A凹み」の据え置き表 |
| 新台入替の日に入れる | 入替の前日・当日・翌日・2 日後 vs 入替に絡まない日 | 「入替/示唆」 |
| 示唆景品が置かれた台は高設定 | `observations.csv` のタグつき台 vs 同じ日の他の台 | 「入替/示唆」 |
| 特定の台番を贔屓する / 末尾 / 角 / 並び | 台番ごとの平均、末尾、同機種の並びの端、隣どうしの連動 | 「台番/日」 |
| 3のつく日などのイベント日・曜日 | 日単位で比較（同じ日の台は連動するので、日を 1 サンプルと数える） | 「台番/日」 |
| ジャグラーよりハナハナが強い | 機種別の推定設定配分・実測出率 | 「A設定」 |
| 年金支給日（とその後）は回収する | 偶数月15日（前倒しあり）と後 3 日 vs それ以外。全台の平均差枚・勝率・稼働 | 「営業日」 |
| 給料日・月初/月末・連休（GW/お盆/年末年始）の扱い | 同上 | 「営業日」 |
| イベント日の前日/翌日は回収する | イベント日の前日・翌日 vs それ以外 | 「営業日」 |
| 出した翌日は締める | 放出日（上位 15%）の翌日 vs それ以外の日の翌日、前日との相関 | 「営業日」の回収日・放出日 |
| 景品示唆のあった日は店全体が強い | `calendar.csv` に書いた日 vs それ以外 | 「営業日」 |
| おすすめ週間は対象機種が強い | 対象機種の期間中 vs ふだん、他機種との差の変化 | 「営業日」のおすすめ期間 |
| イベント日はスマスロだけ / 入替日はどの系統に入れるか | スマスロ・ジャグラー/ハナハナ・その他の分類別 × 日の種類 | 「営業日」の分類別 |

- **q** = その台×日が設定 4 以上である確率。**同日比Δq** = q からその日の全台平均を引いたもの（「出す日かどうか」の影響を消して、台選びの効果だけを見る）。
- 判定チップ「効いてる」は、差がそれなりに大きく（全体平均の 2 割以上）かつ p<0.05 のときだけ出る。
- スマスロなど設定を直接読めない機種は、設定推定はせず、差枚・勝率・稼働を日の種類で束ねて比べる（「営業日」）。
  「稼働が増えたのに差枚・勝率が下がる日」が、客は来るが店は回収している日。
- 年金支給日は年 6 回、入替は月 1〜2 回しか起きない。1 年ぶん貯めても日数が少ないので、こうした種類は「後 3 日」も合わせて見て、
  判定が「やや」止まりでも向きが毎回同じかどうか（直近180日の差の列）を確かめる。
- 据え置きが多い店では、凹んだ台＝低設定のまま翌日も弱いので、凹み狙いは逆効果になる。凹みと据え置きの表はセットで読む。

## 4. 限界と注意

- **実データでの検証はこれから。** このツールはクラウド環境からは実データを取得できず、合成データ（法則を仕込んだ架空のホール）で
  「仕込んだ法則を検出できる」「法則が無いときに『ある』と言わない」ことを確かめた段階。自宅で数か月ぶん取得してからが本番。
- 仮説をたくさん同時に見ているので、p<0.05 でも 20 個に 1 個は偶然でも出る。1 つの表の 1 行だけで決めず、
  ウォークフォワード検証（「狙い台」セクション）が「裏付けあり」になっているかを最後の拠り所にする。
- 記録の偏り: 示唆景品を「当たった時だけ」記録すると必ず効いて見える。見かけたら結果を知る前に（朝のうちに）全部記録する。
  景品が無かった日も「見たが無かった」と分かるようにしておくと良い（例: タグ `景品なし確認` を 1 台ぶんだけ入れる）。
- みんレポの差枚は推定値。一般客の取りこぼし（チェリー等）で実際の機械割は公表値より少し下がるので、
  差枚だけで推定すると全体に低設定寄りに出る（`config.mjs` の `atype.skillLossPct` で補正できる）。BIG/REG 回数で推定する分には影響しない。
- 店は運用を変える。データサイトに載ることを前提に動く店もある。直近のデータで法則が続いているかを毎回見ること。
- 勝ちを保証するものではない。使う金額と時間は先に決めておくこと。

## 5. 毎日の回し方

1. 朝: `node tools/minrepo/run.mjs`（自宅 PC）→ `data/report.html` をスマホで開く →「狙い台」と検証結果を確認
2. 店で: 示唆景品や札を見かけたら、結果を見る前にメモ（→ `observations.csv`）。気になる台はレポート内の「設定判別」に 総G・BIG・REG を入れる
3. 夜か翌朝: 公式台データを見て `counts.csv` を埋める（`run.mjs sheet --date 前日` で記入行が出る）
4. 入替の告知・景品示唆・おすすめ週間を見たら `calendar.csv` に 1 行足す（先の日付でもよい）
5. `node tools/minrepo/run.mjs parse && node tools/minrepo/run.mjs analyze && node tools/minrepo/run.mjs report` で再計算
