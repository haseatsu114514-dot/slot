# タイホウ亀島店 設定狙い分析ツール（min-repo データ）

[みんレポ (min-repo.com)](https://min-repo.com/) が公開しているタイホウ亀島店の日次スロットデータを（手で保存したページや手入力から）取り込んで蓄積し、
「設定が入ってそうな場所・法則性」を自動で分析してレポートにするツール。依存パッケージ無し（Node 18+ のみ）。

分析できるもの:

- **出す日・回収する日（全台の営業カレンダー）** — スマスロを含む全台の平均差枚・勝率・稼働を「日の種類」ごとに比較。
  年金支給日・給料日・月初/月末・連休・入替の前後・イベント前日/翌日は自動でタグ付けし、景品示唆・おすすめ週間などは
  手入力（期間・対象機種の指定可）。回収日/放出日になりやすい種類、出した翌日の扱い、スマスロ/ジャグラー・ハナハナ/その他の
  使い分け、今後 2 週間の見通しまで出す（→ 下の「出す日・回収する日」）
- **ジャグラー / ハナハナの設定推定** — 設定ごとのボーナス確率・機械割（解析サイト掲載値）と、台ごとの 総G・BIG・REG（無ければ差枚）を
  突き合わせて設定1〜6 の確率を計算（ベイズ推定）。店全体・機種別の設定配分、凹み台/据え置き/入替日/示唆景品/台番・末尾・並びの検証、
  翌日の狙い台ランキングとその過去検証、実戦用の設定判別電卓まで（→ 下の「ジャグラー / ハナハナの設定狙い」）
- **イベント日仮説の検証** — 3のつく日 / 4のつく日 / 7のつく日 / 第1土曜日 などの勝率・差枚の uplift と p値（並べ替え検定）、
  月次トレンドと「直近6か月でまだ機能しているか」の判定（→ *4の日を今もやってるか* が分かる）
- **日にち別（1〜31日）・曜日別**のヒートマップ
- **末尾分析** — イベント日ごとの末尾成績、日付末尾一致（13日の末尾3 等）、ゾロ目
- **機種シリーズ別** — 北斗・東京喰種・カバネリ・ゴッド・沖ドキ・ジャグラー・ハナハナ × イベント日、年別推移
  （→ *昔は7の日に北斗* の噂を年別で検証できる）
- **全機種の強さランキング** — ウォッチリスト外も含む全機種を勝率順に集計（サンプル数・直近60日の再集計つき。
  → *グールとカバネリ以外に強い台はないか* が分かる）
- **稼働（G数）の観察** — 差枚・勝率に加えて平均G数の uplift を日にち別/曜日別/イベント日/末尾/機種別すべてで併記
  （→ *高稼働×高勝率 = 客に信じられていて実際に出る日* / *高稼働×低勝率 = 客が集まるだけの回収日* を見分けられる）
- **凹み台の救済傾向** — 直近7日合計差枚バケツ別の当日勝率（イベント日/通常日で比較）
- **新台・増台・減台・撤去の自動検知** — 設置構成の変化から検出し、導入直後の扱いも集計
- **キャラ誕生日・記念日** — config の仮説リスト + シリーズ×(月,日) の自動スキャン

## 使い方（手動が基本）

**サイトへの自動アクセスは既定でオフ**（`config.mjs` の `autoFetch: false`）。自分でブラウザを開いて見たもの・保存したものだけを材料にする。
分析に使うのは**直近 6 か月**（`config.mjs` の `analysis.windowMonths`）。

### 1. 過去半年ぶんを集める（どれか、または組み合わせ）

| やり方 | 手間 | 分かること |
|---|---|---|
| **A. 日別ページを保存する**（1 日 1 ページ） | 半年で約 180 回の保存 | 出す日・回収する日、機種別・末尾・スマスロ等の分類別 |
| **B. 日別の数字だけ写す**（`days.csv`） | 1 日 4 つの数字 | 出す日・回収する日（機種別は出ない） |
| **C. 機種別ページも保存する**（ジャグラー/ハナハナぶん） | 1 日あたり機種数ぶん追加 | 台番ごとの設定推定・凹み台・狙い台（過去ぶん） |

- **A / C**: PC のブラウザでみんレポのこの店の日別ページを開き、「名前を付けて保存」→「ウェブページ、HTML のみ」。
  保存したファイルを `tools/minrepo/data/inbox/` に入れて取り込む。ファイル名は何でもよい（中身から日付と種類を見分ける）。
  機種別ページ（機種名のリンク先。URL に `?kishu=` が付く）も同じフォルダに入れてよい。

  ```sh
  node tools/minrepo/run.mjs import     # 取り込み。直近 6 か月でまだ無い日も表示される
  ```

  取り込めたファイルは `inbox/imported/` へ移る。見分けられなかったファイルは理由つきで残る
  （機種別ページで機種名が分からないときは、ファイル名を `機種名.html` にして入れ直す）。
- **B**: `node tools/minrepo/run.mjs sheet` で `data/manual/days.csv` ができる。1 日 1 行、店全体の
  平均差枚・勝った台数・全台数・平均G数 を書く（勝率を % で書くときは `win` に `41%`、`total` は空）。
  保存ページがある日はそちらが優先され、無い日だけ `days.csv` で埋まる。
- 全部を一度にやらなくてよい。まず A か B で半年ぶんの「日」を揃え、ジャグラー/ハナハナの台番別は
  これからの分を公式台データから `counts.csv` に写していくのが現実的（下の「ジャグラー / ハナハナの設定狙い」）。

### 2. 分析して見る

```sh
# inbox の取り込み → パース → 分析 → 攻略シート/レポート（サイトにはアクセスしない）
node tools/minrepo/run.mjs

# 「狙い日」計算の基準日を指定して作り直す（例: 明日向け）
node tools/minrepo/run.mjs report --date 2026-11-13
```

### 自動取得を使う場合（任意）

みんレポの利用条件を自分で確認し、問題ないと判断した場合だけ使う。既定では動かない。

```sh
node tools/minrepo/run.mjs --backfill             # 過去 6 か月ぶん（config.mjs の backfillMonths）
node tools/minrepo/run.mjs --backfill --limit 60  # 分割して少しずつ
node tools/minrepo/run.mjs fetch                  # 新しい日だけ
```

毎回自動で取りに行かせたいときは `config.mjs` の `autoFetch: true`。その場合の注意は「重要な注意」を参照。

**まず開くのは `data/guide.html`（攻略シート）。** 「次に行くなら何日か・避けるなら何日か」「狙い台」「分かってきた法則（確か / たぶん / 差は見えない）」
「REG 回数の早見表と設定判別の電卓」「換金ギャップの計算」「現地チェックリスト」を、数字の表を読まなくても分かる言葉で 1 ページにまとめたもの。
店のデータがまだ無くても、早見表・電卓・お金の計算だけの版が作れる（`node tools/minrepo/run.mjs guide`）。細かい根拠を見たいときに `report.html` を開く。

レポート（`data/report.html`）は**単一ファイルのダッシュボード**（スマホ対応・固定ナビ・結論サマリー・
「今後2週間の狙い日」・表のヘッダクリックでソート）。LINE や AirDrop で自分のスマホに送ればそのまま開ける。

結果は `tools/minrepo/data/` に出る:

| ファイル | 内容 |
|---|---|
| `guide.html` | 攻略シート（結論だけを言葉でまとめた 1 ページ。スマホ向け） |
| `report.html` | 全部の表が入った本体レポート（色付きテーブル） |
| `report.md` | 上位の発見だけのダイジェスト |
| `days.csv` / `models.csv` / `units.csv` / `suffixes.csv` | 自分で Excel 等で分析する用の生データ |
| `analysis.json` | 全分析結果（レポートに出ない詳細含む） |
| `raw/` | 取り込んだ HTML の置き場（パーサ改良後に `run.mjs parse` で再解釈できる） |
| `inbox/` | 手で保存したページを入れる場所（取り込み済みは `inbox/imported/` へ移る） |
| `manual/` | 手入力の CSV（`days.csv` / `counts.csv` / `observations.csv` / `calendar.csv`） |

仮説の追加・変更は `config.mjs` を編集（イベント日・注目機種・誕生日・凹みの閾値）。
取得し直さなくても `node tools/minrepo/run.mjs parse && node tools/minrepo/run.mjs analyze && node tools/minrepo/run.mjs report` で再計算できる。

## ジャグラー / ハナハナの設定狙い

データをどこから取るか・なぜそれで設定が分かると言えるのか・限界は [DATA_SOURCES.md](DATA_SOURCES.md) にまとめてある。要点だけ:

- みんレポの機種別ページ（台番ごとの差枚・G数）を取り込んであれば、それだけで推定が始まる。
- **BIG・REG 回数が入ると精度が大きく上がる。** 店の公式台データは規約上プログラムで取らないので、見て書き写す:

  ```sh
  # data/manual/ に counts.csv / observations.csv / calendar.csv を用意し、その日の全台ぶんの記入行を足す
  node tools/minrepo/run.mjs sheet --date 2026-11-10
  # → counts.csv の games / bb / rb（分かれば diff）を埋めたら再計算
  node tools/minrepo/run.mjs parse && node tools/minrepo/run.mjs analyze && node tools/minrepo/run.mjs report
  ```

- 現地で見たものは `data/manual/` の CSV に足す（Excel で開いて保存してよい。`#` で始まる行は無視される）:

  | ファイル | 列 | 例 |
  |---|---|---|
  | `days.csv` | `date,avgDiff,win,total,avgGames,note` | `2026-11-10,-85,128,320,3150,` |
  | `counts.csv` | `date,unit,model,games,bb,rb,diff,grape,grapeGames,note` | `2026-11-10,512,マイジャグラーV,6480,28,31,+1850,,,` |
  | `observations.csv` | `date,unit,tag,note` | `2026-11-10,512,示唆景品,台上にお菓子` |
  | `calendar.csv` | `date,dateTo,kind,target,note` | `2026-11-17,,入替,,新台入替 9時開店` |

  `tag` は自由に決めてよい（`示唆景品` `札` `ガックン` など）。同じタグの台が「同じ日の他の台より出たか」をタグごとに検証する。
  `unit` は `501-508`（範囲）や `512/515`（複数）とも書ける。台ではなく**日単位**の示唆（例: カウンターに特定の景品が並んだ日）は
  `calendar.csv` に `2026-11-10,,景品示唆,,` のように書くと、その種類の日が他の日より強いかを検証する。
  `kind` に `入替` か `新台` を含む日は入替日として扱い、それ以外（`取材` `店休明け` など）は種類ごとに別枠で検証する。

- その場で 1 台だけ判別したいとき（レポート内の「設定判別」でも同じことができる）:

  ```sh
  node tools/minrepo/run.mjs judge --model マイジャグラーV --games 3200 --bb 13 --rb 14
  node tools/minrepo/run.mjs judge --model キングハナハナ --games 5000 --bb 20 --rb 15
  node tools/minrepo/run.mjs judge --model マイジャグラーV --games 6000 --diff 1800   # 差枚しか分からないとき
  ```

  ぶどう/ベルの確率は、設定差が小さく掲載値もサイトによって揺れるので現状は収録していない
  （`lib/specs.mjs` の `grape` に設定1〜6 の値を入れると、`--grape 回数 --grape-games 数えたG数` とレポートの入力欄が有効になる）。

  既定では「この店の推定設定配分」を前提にする（低設定が多い店では、少し良い数字が出ても低設定の上振れと見る）。
  一般的な判別ツールと同じ前提にしたいときは `--flat`。

- レポートの見方: 「狙い台」は必ず同じセクションの**検証結果（裏付けあり / 弱い裏付け / 裏付けなし）**とセットで読む。
  「裏付けなし」の間は、台選びより行く日選び（イベント日の検証）を優先する。
- 対象機種とスペック表は `lib/specs.mjs`。新機種が入るとレポートに「スペック未登録」の警告が出るので 1 件足す。
  区切りや「高設定」の定義（既定は設定4以上）は `config.mjs` の `atype`。

## 出す日・回収する日（全台の営業カレンダー）

スマスロなど設定が直接は読めない機種は、差枚と過去の成績を「日の種類」で束ねて店のクセを見る。レポートの「営業日」セクションに出る。

- **自動で付くタグ**: `config.mjs` の `eventDays`（3のつく日 等）とその前日/翌日、年金支給日（偶数月15日。土日なら直前の金曜）と
  その後 3 日、給料日（25日）とその後 3 日、月初/月末、GW・お盆・年末年始、入替の前日/当日/翌日/2〜7日後。
- **手で書くタグ**（`data/manual/calendar.csv`）: 店側の動きで、データからは分からないもの。

  ```csv
  date,dateTo,kind,target,note
  2026-11-10,,景品示唆,,カウンターに特定の景品が並んだ
  2026-11-10,2026-11-16,おすすめ週間,北斗|カバネリ,店内POPのおすすめ機種
  2026-11-17,,入替,,新台入替 9時開店
  ```

  `dateTo` に終わりの日を書くと期間になる（`date` に `2026-11-10〜2026-11-16` と書いてもよい）。
  `target` は対象機種名への正規表現で、書くと「対象機種が期間中に、ふだんより・他機種より強かったか」を検証する。
  これから先の日付で書いておくと「今後2週間の見通し」に反映される（入替日はジャグラー/ハナハナの狙い台の採点にも反映）。
- **台単位の示唆**（`observations.csv`）は全機種で検証する（スマスロは同じ日の他の台との差枚で比較）。
  景品の種類ごとにタグを分けて書くと、どの景品が本物の示唆かを別々に見られる。
- **見方**:
  - 「日の種類別」の**差**がプラスで p が小さい → その種類の日は店全体が出している。マイナスで p が小さい → 回収している。
  - **稼働が増えているのに差枚・勝率が下がる**種類は「客は来るが店は回収」の日（年金支給日や給料日の後で起きやすい形）。
  - 「曜日調整後の差」も同じ向きなら、土日と重なっただけの見かけの効果ではない。
  - 「回収日・放出日の出方」で、出した翌日に締める店かどうかが分かる。
  - 「機種の分類別」で、イベント日はスマスロだけ・入替日はジャグラーにも、といった使い分けを見る。
  - 種類どうしは重なる（お盆と 8 月の年金支給日など）。片方しか効いていないこともあるので、日数の多い方・曜日調整後も残る方を信じる。
  - 年金支給日は年 6 回、入替も月 1〜2 回しか無い。1 年ぶんでも「やや」止まりのことが多いので、結論を急がない。
- 区切りの変更は `config.mjs` の `calendar`（回収日/放出日の割合、機種の分類）。

## 重要な注意

- **既定ではサイトに自動アクセスしない。** 手で保存したページと手入力の CSV だけで動く。以下 2 点は自動取得を使う場合だけの注意。
- （自動取得を使う場合）**自宅回線で実行すること。** min-repo はデータセンター系 IP からのアクセスに *ダミー値*（差枚 0/±1・出率 100% 張り付き）や
  空の応答を返す。本ツールはダミー値を検知すると即中断する。サイト側が機械的なアクセスを歓迎していない合図でもあるので、利用条件を確認してから使うこと。
- （自動取得を使う場合）**マナー**: リクエスト間隔は既定 2 秒 + ジッタ。短くしないこと。バックフィルは `--limit` で数日に分ける。
- **店の公式台データ（台データオンライン系）はプログラムで取得しない。** 規約がデータベースの複製と第三者への提供を禁じている。
  見て `counts.csv` に写すのは自分用のメモの範囲に留め、公開・共有しないこと。
- **私的利用の範囲で。** データは min-repo の独自調査値（推定値）であり、レポートや CSV を再配布・転載しないこと。
  このリポジトリを GitHub Pages 等で公開している場合も `tools/minrepo/data/` は公開に含めない（.gitignore 済み）。
- 機種別詳細（`?kishu=`）はリクエスト数が増える。既定はウォッチリスト該当機種のみ・毎日取得
  （`config.mjs` の `kishuDetail.days: "event"` にするとイベント日+土日だけになり大幅に減る。`--no-kishu` で無効化）。
- 古い記事（おおよそ 2020 年以前）はページ構成が違い、タイトルの「総差枚/平均差枚」だけ取り込まれる。

## 新台・増台の情報源について

- 過去の入替は本ツールが**データから自動検知**する（`report.html` の「新台・増台・撤去の検知」）。
- これからの入替（導入予定）はデータからは分からないので、
  [P-town の店舗ページ](https://p-town.dmm.com/shops/aichi/5713)（新台機種情報）や店の公式 X を見るのが早い。
  旧イベント日・口コミは [みんパチの店舗ページ](https://minpachi.com/%E3%82%BF%E3%82%A4%E3%83%9B%E3%82%A6%E4%BA%80%E5%B3%B6%E5%BA%97/) にまとまっている。

## 仕組み

1. 手で保存したページを `data/inbox/` から取り込み、日付ごとに `data/raw/YYYY-MM-DD.html` へ置く
   （自動取得を使う場合は、WordPress REST API で記事一覧を列挙して各日の HTML を取得する）
2. 手入力の CSV（`data/manual/`）を読み込む
3. テーブル（概況 / 機種別 / バラエティ台番別 / 末尾別）をパースして tidy な CSV / JSON に変換
4. 分析（並べ替え検定・符号反転検定で p値を出す）→ HTML / Markdown レポート生成

```
tools/minrepo/
  run.mjs          エントリポイント（import / parse / analyze / report / guide / sheet / judge、任意で fetch）
  config.mjs       店・仮説・マナーの設定
  lib/parse.mjs    HTML パーサ（純粋関数）
  lib/dataset.mjs  tidy データ化・CSV 出力（純粋関数）
  lib/analyze.mjs  分析エンジン（純粋関数）
  lib/report.mjs   レポート生成（純粋関数）
  lib/import.mjs   手で保存したページの判別（店全体ページ / 機種別ページ、日付・機種名の読み取り）
  lib/wp.mjs       記事一覧の列挙（自動取得を使う場合のみ）
  lib/http.mjs     行儀のよい fetch（自動取得を使う場合のみ）
  lib/util.mjs     数値・日付・統計
  lib/specs.mjs    ジャグラー/ハナハナの設定別スペック表（確認元つき）と機種名の照合
  lib/settei.mjs   設定推定の計算（尤度・事後確率・設定配分の EM 推定）
  lib/atype.mjs    ジャグラー/ハナハナの仮説検証・狙い台ランキング・ウォークフォワード検証
  lib/manual.mjs   手入力 CSV（counts / observations / calendar）の読み込みと統合
  lib/report-atype.mjs  上記のレポート部品と設定判別電卓
```

## 読み方のコツ

- 差枚は万枚事故などの外れ値に弱い。**勝率の uplift と p値**を主に、差枚・中央値を従に見る。
- G数（稼働）は客側の行動。高稼働=高設定の証明ではないが、イベント日が客に信じられているかの傍証になる。
  稼働だけ高くて勝率が伸びない日は「バレてるだけの回収日」の疑い。
- p値が 0.05 を切っていても、仮説をたくさん同時に見ているので 20 回に 1 回は偶然でもそうなる。
  「uplift の大きさ」「月次トレンドの安定感」「n」をセットで判断すること。
  反復数（サンプル数）は `config.mjs` の `analysis.iterations`（既定 4000）で増やせる。
- 店が「データサイトに載る数字」を意識して営業を変える可能性もある。過去の法則は未来を保証しない。
